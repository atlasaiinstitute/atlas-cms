# ATLAS CMS database architecture — Step 03

## Scope

This stage defines the Supabase PostgreSQL relational model for organizations, communities, shared user identities, governance, events, content, resources, communications and system management. It does not implement authentication, registration, frontend authorization, or RLS policies.

The migration is `supabase/migrations/20261106170000_initial_atlas_schema.sql`. It is additive and uses `create table if not exists`, `create index if not exists`, and non-destructive trigger replacement. Development fixtures are isolated in `supabase/seed.sql` and use deterministic placeholder IDs and non-personal organization/community records.

## Tenant model

`organizations` is the top-level tenant. `communities` belongs to an organization through `organization_id`. Community-owned records carry both `organization_id` and `community_id` where relevant. Organization-wide records use a nullable `community_id`. Shared people are represented by `user_profiles`; membership is modeled separately through `organization_memberships` and `community_memberships`, allowing one user to belong to multiple communities.

The database never treats a client-supplied organization ID as proof of authorization. Future server-side services must resolve the authenticated identity, verify membership/role scope, and rely on PostgreSQL RLS as the final enforcement layer.

## Integrity protections

All primary keys use UUIDs generated by `pgcrypto`. Foreign keys use explicit delete behavior. Slugs are constrained and unique within their tenant. Memberships have a unique `(community_id, user_id)` relationship and a partial active-membership index. Committee membership has one chairperson and one secretary per committee through partial unique indexes. Event registrations and attendance are unique per event/user. Committee terms and event date ranges have check constraints. All mutable tables use UTC `created_at` and `updated_at` timestamps with the shared `set_updated_at()` trigger function.

## Supabase assumptions

The `user_profiles.id` foreign key references `auth.users(id)` because Supabase owns the authentication identity table. No auth user is inserted by the seed. Supabase Storage is represented by `storage_path` metadata in `resources` and `application_documents`; binary content does not live in PostgreSQL.

## Tables requiring RLS in the security stage

All of the following require tenant-aware RLS before any production data is exposed: `organizations`, `user_profiles`, `organization_memberships`, `organization_settings`, `organization_domains`, `communities`, `community_memberships`, `membership_applications`, `application_reviews`, `application_documents`, `committees`, `committee_members`, `committee_meetings`, `committee_minutes`, `committee_resolutions`, `appointments`, `events`, `event_registrations`, `event_attendance`, `content_categories`, `content_items`, `content_revisions`, `publications`, `resource_categories`, `resources`, `resource_access_rules`, `announcements`, `notifications`, `conversations`, `conversation_members`, `messages`, `user_role_assignments`, and `audit_logs`.

The future RLS work should define authenticated-user membership helpers, organization-scoped policies, community-scoped policies, role checks, storage policies, and append-only audit behavior. It should also test cross-tenant reads/writes and verify that service-role operations remain server-only.

## TypeScript integration

Core row contracts are maintained in `src/types/database.ts`, separate from UI code. A future Supabase CLI type-generation step can replace or augment the `Database` map while preserving the exported domain interfaces used by services and feature modules.

## Local verification

If Supabase credentials or a local Postgres runtime are unavailable, validate migration structure locally and do not claim remote application. Recommended later commands are:

```bash
supabase db reset
supabase gen types typescript --local > src/types/supabase.ts
```

Neither command is run in this stage unless a Supabase project/local database is explicitly configured.
